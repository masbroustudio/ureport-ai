# Architecture Decision Records (ADR)

## Overview

Dokumen ini berisi catatan keputusan arsitektur (Architecture Decision Records) untuk project uReport AI v2. Setiap ADR mencatat konteks, keputusan, alasan, dan konsekuensi dari pilihan teknis yang signifikan.

---

## ADR-001: FastAPI sebagai Backend Utama

**Status:** Accepted
**Date:** 2025-05-27

### Context

Perlu memilih backend framework utama untuk uReport AI v2. Opsi yang dipertimbangkan:
- Next.js API Routes sebagai backend monolitik (full-stack JS)
- FastAPI sebagai backend terpisah dengan Next.js hanya untuk frontend
- NestJS (TypeScript backend framework)
- Django (Python full-stack framework)

Project ini sangat bergantung pada ekosistem Python untuk AI/ML (LangGraph, LlamaIndex, pandas, WeasyPrint). Perlu framework yang async-native dan memiliki developer experience yang baik.

### Decision

Menggunakan **FastAPI** sebagai backend utama (primary API server). Next.js digunakan hanya untuk frontend dan thin BFF (Backend-for-Frontend) layer untuk auth dan edge caching.

### Rationale

1. Ekosistem Python untuk AI/ML tidak tertandingi (LangGraph, LlamaIndex, sentence-transformers, pandas, dll.)
2. Async native - FastAPI dibangun di atas Starlette dan ASGI, mendukung async/await penuh
3. Auto-generated OpenAPI documentation (Swagger UI + ReDoc)
4. Pydantic v2 integration - validasi data yang sangat kuat dan cepat
5. Dependency Injection system yang elegan dan testable
6. Performance mendekati NodeJS/Go untuk I/O-bound operations
7. Type hints Python memberikan autocomplete dan error detection yang baik
8. Mature ecosystem untuk background jobs (Celery), ORM (SQLAlchemy), dan migrations (Alembic)

### Consequences

- Developer perlu menguasai Python dan TypeScript (dua bahasa)
- Perlu manage dua deployment (frontend + backend)
- Network latency antara frontend dan backend (dimitigasi dengan server actions dan caching)
- Perlu setup CORS dan authentication antara services
- Docker menjadi requirement untuk development consistency

### Alternatives Rejected

- **Next.js API Routes (monolith):** Ekosistem AI di JavaScript sangat terbatas dibanding Python. LangChain.js kurang mature. Tidak ada padanan pandas, WeasyPrint, sentence-transformers.
- **NestJS:** JavaScript ecosystem yang sama terbatasnya untuk AI. Lebih verbose dibanding FastAPI.
- **Django:** Terlalu monolitik dan opinionated. Async support masih belum mature. ORM-nya kurang flexible dibanding SQLAlchemy. Overhead yang tidak perlu untuk API-only service.

## ADR-002: LiteLLM sebagai Gateway LLM (bukan raw SDK per provider)

**Status:** Accepted
**Date:** 2025-05-27

### Context

uReport AI menggunakan multiple LLM providers: Cerebras, Groq, Google Gemini, dan Sumopod (custom/self-hosted). Setiap provider memiliki SDK dan API format yang sedikit berbeda. Perlu strategi untuk mengakses semua provider secara unified.

Opsi:
- Raw SDK per provider dengan adapter pattern manual
- LangChain sebagai abstraction layer
- LiteLLM sebagai unified gateway
- Custom adapter pattern (Strategy Pattern)

### Decision

Menggunakan **LiteLLM** sebagai unified LLM gateway. Semua LLM calls melalui LiteLLM API yang menyediakan interface OpenAI-compatible untuk 100+ providers.

### Rationale

1. Satu SDK untuk semua providers - `litellm.completion()` bekerja untuk Groq, Cerebras, Gemini, dan custom endpoints
2. Built-in fallback dan retry - jika satu provider down, otomatis switch ke alternatif
3. Built-in cost tracking - monitor spending per provider/model tanpa kode tambahan
4. Caching support (in-memory dan Redis) - reduce cost dan latency untuk repeated queries
5. Load balancing - distribusi request antar providers berdasarkan latency atau round-robin
6. Minimal code maintenance - tidak perlu update adapter setiap kali provider mengubah API
7. Custom API base support - Sumopod (self-hosted) bisa dikonfigurasi via `api_base` parameter
8. Streaming support yang konsisten antar semua providers

### Consequences

- Dependency pada library third-party (LiteLLM) - perlu monitor updates dan breaking changes
- Sedikit overhead abstraction (negligible untuk production use)
- Beberapa fitur provider-specific mungkin tidak ter-expose melalui unified API
- Perlu testing compatibility setiap ada update LiteLLM version
- Debugging errors perlu memahami layer tambahan antara code dan provider

### Alternatives Rejected

- **Raw SDK per provider (Strategy Pattern manual):** Lebih banyak code untuk maintain, harus menulis fallback/retry/caching sendiri, setiap provider update perlu update adapter. Reinventing the wheel.
- **LangChain only:** Less control over routing dan fallback behavior. LangChain's LLM abstraction lebih opinionated dan tightly coupled dengan chain ecosystem.
- **Custom adapter pattern:** Effort besar untuk fitur yang sudah ada di LiteLLM. Cost tracking dan load balancing harus dibangun dari nol.

## ADR-003: Qdrant sebagai Vector Database (bukan pgvector)

**Status:** Accepted
**Date:** 2025-05-27

### Context

RAG (Retrieval-Augmented Generation) pipeline membutuhkan vector storage dan similarity search yang efisien. Perlu memilih antara:
- pgvector (PostgreSQL extension) - menambah vector capabilities ke existing PostgreSQL
- Qdrant (dedicated vector database)
- Weaviate (dedicated vector database)
- Chroma (embedded vector database)

Di versi sebelumnya (v1), keputusan awal adalah menggunakan pgvector. Namun setelah evaluasi ulang untuk v2 yang membutuhkan hybrid search dan scaling yang lebih baik, keputusan ini di-revisi.

### Decision

Menggunakan **Qdrant** sebagai dedicated vector database, menggantikan keputusan awal pgvector di v1.

### Rationale

1. Performance yang lebih baik di scale - purpose-built HNSW implementation yang dioptimasi untuk vector search
2. Hybrid search native - mendukung sparse vectors (BM25) + dense vectors dalam satu query tanpa konfigurasi tambahan
3. Tidak ada resource contention dengan main database - PostgreSQL fokus untuk relational data, Qdrant fokus untuk vectors
4. Payload filtering yang powerful - filter berdasarkan metadata tanpa mengorbankan search performance
5. Mudah di-Docker - satu container, zero configuration, REST + gRPC API
6. Built-in quantization (scalar, product, binary) - reduce memory usage 4-32x
7. Multi-tenancy support - isolasi data per user/organization via payload filtering
8. Active development dan community - updates frequent, production-proven (Dropbox, Microsoft, dll.)
9. Web UI dashboard included - monitoring dan debugging tanpa tools tambahan

### Consequences

- Tambahan satu service untuk di-manage (Docker container)
- Data vectors terpisah dari relational data (perlu sync strategy)
- Backup dan recovery terpisah dari PostgreSQL
- Tambahan network hop untuk vector search (negligible latency via gRPC)
- Learning curve untuk Qdrant-specific concepts (payload, scroll, recommend)
- Perlu strategy untuk keep vector data in sync dengan relational data

### Alternatives Rejected

- **pgvector:** Baik untuk skala kecil (< 1M vectors), tapi resource competition dengan main DB queries. Hybrid search harus di-implement manual. HNSW di pgvector masih inferior dibanding dedicated solution. Ketika DB load tinggi, vector search jadi lambat.
- **Weaviate:** Lebih complex setup, schema-ful (harus define class), heavier resource usage. Overkill untuk use case kita.
- **Chroma:** Bagus untuk prototyping tapi kurang production-ready. In-memory default, persistence masih beta. Kurang fitur filtering.

## ADR-004: LangGraph untuk Agent Orchestration (bukan plain LangChain)

**Status:** Accepted
**Date:** 2025-05-27

### Context

uReport AI memiliki agent yang perlu mengorkestrasikan multiple tools: RAG retrieval, data analysis, chart generation, report writing. Agent perlu:
- Branching logic (if data analysis needed, do X; if RAG needed, do Y)
- Retry dan error recovery
- Human-in-the-loop untuk approval sebelum generate report
- State persistence antar interactions
- Predictable dan debuggable execution flow

Opsi:
- Plain LangChain AgentExecutor (ReAct loop)
- LangGraph (state machine / graph-based orchestration)
- CrewAI (multi-agent framework)
- Custom orchestration (manual state management)

### Decision

Menggunakan **LangGraph** untuk agent orchestration. Agent didefinisikan sebagai state machine dengan explicit nodes dan edges, bukan implicit ReAct loop.

### Rationale

1. Predictable state transitions - setiap node memiliki input/output yang jelas, tidak ada unpredictable loops
2. Visualizable graph - bisa generate diagram dari graph definition untuk debugging dan dokumentasi
3. Conditional routing native - `add_conditional_edges()` untuk branching logic yang explicit
4. Human-in-the-loop support built-in - interrupt graph execution, wait for user input, resume
5. Checkpointing dan persistence - save/restore state antar sessions (penting untuk long-running report generation)
6. Retry dan error handling per-node - jika satu step gagal, bisa retry tanpa mengulang seluruh flow
7. Streaming events dari setiap node - user bisa melihat progress real-time
8. Subgraph composition - complex workflows bisa dipecah menjadi reusable subgraphs
9. Better debugging - trace execution path, inspect state di setiap step

### Consequences

- Learning curve lebih tinggi dibanding plain LangChain
- More boilerplate code untuk graph definition (tapi lebih maintainable)
- Perlu careful state design (TypedDict dengan proper annotations)
- Tightly coupled dengan LangChain ecosystem (tapi bisa wrap non-LangChain tools)
- Graph visualization memerlukan additional tooling
- Testing perlu mock setiap node function

### Alternatives Rejected

- **Plain LangChain AgentExecutor:** Unpredictable execution loops, sulit di-debug ketika agent stuck. Tidak ada built-in human-in-the-loop. State management minimal. Sulit implement branching yang complex.
- **CrewAI:** Designed untuk multi-agent collaboration, overkill untuk single-agent use case. Abstraction terlalu tinggi, kurang control. Dependency tambahan yang besar.
- **Custom orchestration:** Effort besar untuk implement state management, checkpointing, retry, dan streaming dari nol. Reinventing apa yang LangGraph sudah sediakan.

## ADR-005: WeasyPrint untuk PDF Generation (bukan Puppeteer)

**Status:** Accepted
**Date:** 2025-05-27

### Context

uReport AI perlu menghasilkan laporan PDF profesional dengan fitur:
- Table of Contents (daftar isi) otomatis
- Page numbers (nomor halaman)
- Headers dan footers per-section
- Embedded charts dan images
- Consistent formatting dan typography
- Reproducible output

Opsi:
- Puppeteer/Playwright (headless Chrome/Chromium rendering)
- WeasyPrint (HTML + CSS Paged Media to PDF)
- ReportLab (Python low-level PDF generation)
- wkhtmltopdf (deprecated WebKit-based converter)
- Pandoc (Markdown to PDF via LaTeX)

### Decision

Menggunakan **WeasyPrint** untuk konversi HTML + CSS ke PDF menggunakan CSS Paged Media specification.

### Rationale

1. Native Python - tidak memerlukan Chromium binary (reduce Docker image size 500MB+)
2. Resource usage lebih ringan - tidak perlu headless browser process yang memory-intensive
3. CSS Paged Media support - @page rules, named pages, running elements, page counters
4. Jinja2 templates natural - HTML templates yang familiar untuk developer web
5. Reproducible output - same input always produces same PDF (deterministic)
6. Page break control yang presisi - break-before, break-after, break-inside, orphans, widows
7. Header/footer support via running elements dan @page margin boxes
8. Cross-references dan bookmarks - target-counter() untuk ToC generation
9. Font embedding native - @font-face works out of the box
10. Fast generation untuk dokumen medium-size (1-50 pages dalam < 10 detik)

### Consequences

- CSS Paged Media memiliki learning curve tersendiri (berbeda dari CSS biasa)
- Beberapa CSS features tidak supported (flexbox/grid di paged context masih terbatas)
- Complex charts harus di-render sebagai image terlebih dahulu (SVG atau PNG)
- Performance bisa jadi issue untuk dokumen sangat besar (100+ pages) - dimitigasi dengan chunked generation
- Browser-specific CSS properties tidak bekerja (hanya W3C standard)
- Debugging layout harus dilakukan via generated PDF (tidak ada live preview)
- Dependencies system libraries (cairo, pango, gdk-pixbuf) harus ada di Docker image

### Alternatives Rejected

- **Puppeteer/Playwright:** Membutuhkan Chromium binary (700MB+), memory-intensive (300-500MB per instance), non-deterministic rendering (slight variations antar versions). Overkill untuk document generation.
- **ReportLab:** Terlalu low-level. Harus mendefinisikan setiap elemen secara programmatik (coordinates, sizes). Tidak bisa pakai HTML/CSS templates. Developer productivity rendah.
- **wkhtmltopdf:** Deprecated, menggunakan versi WebKit lama, CSS support terbatas, security vulnerabilities yang tidak di-patch.
- **Pandoc:** Bagus untuk Markdown-to-PDF sederhana, tapi sangat terbatas untuk layout complex (multi-column, custom headers, embedded charts). Memerlukan LaTeX untuk output berkualitas.

## ADR-006: Celery untuk Background Jobs (bukan BullMQ)

**Status:** Accepted
**Date:** 2025-05-27

### Context

Report generation di uReport AI membutuhkan waktu 30-120 detik (LLM generation + data analysis + PDF rendering). Proses ini tidak bisa dilakukan secara synchronous dalam HTTP request. Perlu background job processing system dengan fitur:
- Async task execution
- Retry mechanism dengan exponential backoff
- Progress tracking (user melihat progress bar)
- Task chaining (step 1 selesai, trigger step 2)
- Priority queues (premium users didahulukan)
- Monitoring dan observability

Opsi:
- Celery 5 (Python, Redis/RabbitMQ broker)
- BullMQ (Node.js, Redis-based)
- RQ (Redis Queue - Python, simpler)
- Arq (Python, asyncio-native)
- Dramatiq (Python, alternative to Celery)

### Decision

Menggunakan **Celery 5** dengan Redis sebagai message broker untuk semua background job processing.

### Rationale

1. Python native - same ecosystem dengan FastAPI backend, share models dan utilities tanpa duplikasi
2. Mature dan battle-tested - 10+ tahun development, digunakan oleh Instagram, Mozilla, Robinhood
3. Rich feature set:
   - Chains: sequential task execution (generate text -> create charts -> render PDF)
   - Groups: parallel execution (generate semua BAB secara paralel)
   - Chords: parallel then aggregate (generate BAB paralel, lalu compile menjadi satu PDF)
4. Retry mechanisms yang sophisticated - autoretry_for, max_retries, countdown, exponential backoff
5. Monitoring via Flower - web UI untuk melihat task status, worker health, queue depth
6. Redis broker sudah ada di stack (juga dipakai untuk caching dan session)
7. Priority queues - bisa route tasks ke different queues berdasarkan priority
8. Rate limiting per-task - prevent overwhelming LLM APIs
9. Task result tracking - store results di Redis untuk progress polling
10. Periodic tasks via Celery Beat - untuk scheduled jobs (cleanup, reporting)

### Consequences

- Tambahan worker process yang harus di-manage (selain API server)
- Redis menjadi single point of failure untuk job queue (dimitigasi dengan Redis persistence)
- Serialization overhead (task arguments harus JSON-serializable)
- Debugging distributed tasks lebih complex dibanding synchronous code
- Memory usage worker bisa tinggi jika tasks memory-intensive (pandas DataFrames)
- Perlu careful task design (idempotent, retry-safe)
- Cold start time untuk worker (loading models, establishing connections)

### Alternatives Rejected

- **BullMQ:** Node.js based - membutuhkan service terpisah dalam bahasa berbeda. Tidak bisa share Python models/utilities. Cross-language communication overhead. Tim harus maintain kode di dua bahasa untuk satu fitur.
- **RQ (Redis Queue):** Lebih simple tapi fitur terbatas. Tidak ada chains/groups/chords. Monitoring kurang mature. Retry mechanism basic.
- **Arq:** Asyncio-native (bagus), tapi ekosistem lebih kecil. Kurang monitoring tools. Community kecil, kurang battle-tested di production scale.
- **Dramatiq:** Alternative yang baik ke Celery (lebih modern API), tapi community lebih kecil, kurang plugins/integrations, dan tidak ada padanan Celery Beat yang matang.

## Summary

| ADR | Keputusan | Alasan Utama |
|-----|-----------|-------------|
| ADR-001 | FastAPI sebagai backend utama | Python ecosystem untuk AI/ML tidak tertandingi |
| ADR-002 | LiteLLM sebagai LLM gateway | 1 SDK untuk 100+ providers, built-in fallback/retry/caching |
| ADR-003 | Qdrant sebagai vector database | Better performance, hybrid search native, no resource contention |
| ADR-004 | LangGraph untuk agent orchestration | Predictable state machine, debuggable, human-in-the-loop |
| ADR-005 | WeasyPrint untuk PDF generation | Native Python, ringan, CSS Paged Media, no Chromium dependency |
| ADR-006 | Celery untuk background jobs | Python native, mature, chains/groups/chords, Flower monitoring |

> **Note:** ADR bersifat immutable setelah accepted. Jika keputusan perlu diubah, buat ADR baru yang supersede ADR lama (contoh: ADR-007 supersedes ADR-003).
