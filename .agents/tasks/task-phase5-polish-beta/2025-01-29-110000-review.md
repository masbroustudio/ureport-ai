# Production hardening and UX polish for uReport AI (v2)

Phase 5 adds backend production infrastructure (rate limiting, request tracing, metrics, Sentry, Docker deployment) and frontend UX polish (onboarding, empty states, error handling with toasts/retry/offline, mobile sidebar, dark mode charts, PWA). All six v1 issues were fixed in the latest commit. One new concern emerged during verification.

**Watch for:** `NEXT_PUBLIC_API_URL=http://api:8000` in compose.prod.yml is a Docker-internal hostname that browsers cannot resolve — all client-side API calls will fail in production (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The Docker Compose configuration sets `NEXT_PUBLIC_API_URL=http://api:8000` as the API base URL for the web service. `NEXT_PUBLIC_` environment variables are inlined into the client-side JavaScript bundle at build time by Next.js, so the browser will attempt to reach `http://api:8000` — a hostname that only resolves within the Docker network. Every `apiFetch`, file upload, and SSE connection from the browser will fail with a DNS resolution error. Since nginx already proxies `/api/` to the backend, the simplest fix is to make the frontend default to relative URLs (empty string fallback in `api.ts`) and remove `NEXT_PUBLIC_API_URL` from the compose file.

All six v1 issues were verified as fixed: single worker, network-first SW for navigation, clean retry, no exposed ports, restricted metrics, useEffect for dark mode.

## Client-side API base URL points to unreachable Docker hostname

The compose file sets:

```yaml
web:
  environment:
    - NEXT_PUBLIC_API_URL=http://api:8000
```

Next.js inlines `NEXT_PUBLIC_*` variables into the client bundle at build time. The multi-stage Dockerfile runs `pnpm build` inside Docker where this variable is available, so the resulting JavaScript will contain `http://api:8000` as the fetch target. When a user's browser loads the page, every call in `api.ts`, `ChatComposer.tsx`, `OnboardingModal.tsx`, `FileUpload.tsx`, `KBUpload.tsx`, and `reports/[id]/page.tsx` will try to connect to `http://api:8000`, which doesn't exist outside the Docker network.

The nginx config already routes `/api/` to the backend:

```nginx
location /api/ {
    proxy_pass http://api_backend;
}
```

The cleanest fix: remove `NEXT_PUBLIC_API_URL` from compose.prod.yml entirely and change `api.ts` to default to an empty string (relative path) rather than `http://localhost:8000`:

```typescript
// api.ts
const API_BASE = process.env.NEXT_PUBLIC_API_URL || "";
```

This makes all fetches relative (e.g., `/api/v1/conversations/...`) which nginx will proxy correctly regardless of domain. The same change should be applied to the other 4 components that read `NEXT_PUBLIC_API_URL` directly (`ChatComposer`, `OnboardingModal`, `FileUpload`, `KBUpload`) — or better, have them use the centralized `apiFetch` helper instead of raw `fetch`.
