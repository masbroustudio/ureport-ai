# Production hardening and UX polish for uReport AI

Phase 5 adds two major concerns: backend production infrastructure (rate limiting, request tracing, metrics, Sentry, Docker deployment) and frontend UX polish (onboarding, Indonesian localization, offline awareness, mobile sidebar, dark mode charts, PWA). The backend work introduces in-memory rate limiting with per-user JWT identification, structured JSON logging, a minimal Prometheus metrics stub, and conditional Sentry init. The frontend adds a 3-step onboarding modal, toast notifications via Sonner, retry on failed messages, a service worker for cache-first offline, and a responsive off-canvas sidebar. Production deployment gets multi-stage Dockerfiles, a full Docker Compose stack (7 services), and nginx reverse proxy.

**Watch for:** In-memory rate limiting resets on every deploy/restart and doesn't share state across workers (confirmed). The service worker caches HTML routes with a cache-first strategy that can serve stale pages indefinitely with no revalidation path (confirmed). The `retry` function in `useChat` calls `setMessages` inside itself recursively which is a React anti-pattern (confirmed). The nginx `/metrics` endpoint is world-accessible in the default config (confirmed).

## High-level view

The rate limiter uses an in-memory dictionary keyed by user ID (from JWT) or client IP. It works for single-process development but the uvicorn `--workers 4` command in the Dockerfile means each worker has its own independent limit state, effectively multiplying the real limit by the worker count. There's no Redis-backed rate limiting despite Redis being in the compose stack.

The service worker registers a cache-first strategy for GET requests with no TTL, no version-bump mechanism beyond changing the `CACHE_NAME` constant, and no network-first fallback for HTML pages. In a deploy-frequently environment, users can be stuck on stale cached pages until they manually clear the cache or the developer remembers to bump the cache name.

The onboarding modal stores the chosen model in localStorage (`default_model`) but nothing reads it back when sending messages. The model selection in onboarding is decorative unless the chat composer or useChat hook consumes this preference.

The Docker Compose production config exposes both `api:8000` and `web:3000` directly on the host alongside nginx on port 80, defeating the purpose of the reverse proxy as a single entry point.

The retry mechanism in `useChat` calls `setMessages` and inside that callback calls `setMessages` again and `sendMessage` via `setTimeout(0)`. This is a state update during a state update, which React may batch unpredictably. The simpler pattern would be to extract the user message content outside the setter.

## In-memory rate limiting vs. multi-worker deployment

The rate limiter maintains a `defaultdict(list)` of timestamps keyed by user or IP. This is correct for a single-process server, but the production Dockerfile launches with `--workers 4`:

```dockerfile
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "4"]
```

Each worker forks a separate process, each with its own `_requests` dict. A user can effectively make `4 * 60 = 240` requests per minute across workers before being limited. The Redis service is already in the compose stack — rate limit state should live there. Alternatively, for a FastAPI async app, a single uvicorn process with `--loop uvloop` is the standard production pattern (multiple workers are for sync frameworks); this would make in-memory state correct again.

The cleanup logic (`_cleanup_expired`) runs synchronously on every request; under load this iterates all keys. For a small user base this is fine, but the `CLEANUP_INTERVAL` gate (every 5 minutes) mitigates it well enough for now.

## Service worker cache strategy

```javascript
self.addEventListener('fetch', (event) => {
  if (event.request.method !== 'GET') return;
  event.respondWith(
    caches.match(event.request).then((cached) => cached || fetch(event.request))
  );
});
```

This is a cache-first strategy for all GET requests, including HTML navigation. Once `/chat` is cached, the user will never see a newer version of that page unless the `CACHE_NAME` constant changes and the old cache is evicted during the `activate` event. There is no mechanism to notify the user of an update, no `skipWaiting()` prompt, and no network-first fallback for `text/html` requests.

For an app that deploys frequently, this will cause support tickets from users running stale frontends. At minimum, navigation requests (those with `mode: 'navigate'` or `Accept: text/html`) should use network-first with cache fallback.

## Retry mechanism state management

```typescript
const retry = useCallback(() => {
  if (failedMessageIndex === null) return;
  setMessages((prev) => {
    const userMsgIndex = failedMessageIndex - 1;
    if (userMsgIndex < 0) return prev;
    const userMsg = prev[userMsgIndex];
    if (!userMsg || userMsg.role !== "user") return prev;
    const updated = prev.slice(0, userMsgIndex);
    setMessages(updated);  // <-- nested setMessages call inside setMessages updater
    setTimeout(() => {
      sendMessage(userMsg.content);
    }, 0);
    return updated;
  });
}, [failedMessageIndex, sendMessage]);
```

The outer `setMessages` takes an updater function. Inside that updater, `setMessages(updated)` is called again, and `sendMessage` is triggered via `setTimeout`. The inner `setMessages` is redundant (the outer updater already returns `updated`), and `setTimeout` inside an updater relies on React's batching guarantees in ways that differ between React 18 strict mode and production. A cleaner approach:

```typescript
const retry = useCallback(() => {
  if (failedMessageIndex === null) return;
  const msgs = messages; // read from ref or state
  const userMsg = msgs[failedMessageIndex - 1];
  if (!userMsg || userMsg.role !== "user") return;
  setMessages(msgs.slice(0, failedMessageIndex - 1));
  sendMessage(userMsg.content);
}, [failedMessageIndex, messages, sendMessage]);
```

## Docker Compose port exposure

The compose file maps both service ports directly to the host:

```yaml
api:
  ports:
    - "8000:8000"
web:
  ports:
    - "3000:3000"
nginx:
  ports:
    - "80:80"
    - "443:443"
```

If the intent is that nginx is the sole entry point, the api and web services should not publish ports to the host. This allows bypassing nginx (and its rate limiting, request ID injection, and eventual SSL termination). Either remove the `ports:` directives from api/web, or bind them to 127.0.0.1 only for debug access.

## Onboarding model selection is write-only

The `OnboardingModal` stores `localStorage.setItem("default_model", selectedModel)` but there's no code in `useChat`, `ChatComposer`, or any other component that reads `default_model` from localStorage. The user selects a model during onboarding but it has no effect on subsequent requests.

## PlotlyChart dark mode detection

```typescript
const isDark =
  typeof document !== "undefined" &&
  document.documentElement.classList.contains("dark");
```

This runs during the render phase. In Next.js with SSR/SSG, `document` is undefined on the server and the check short-circuits to `false`. On the client, during hydration, the value may not match what the server rendered (the dark class is typically applied via a client-side script). This causes a hydration mismatch warning. The component should read the theme from a React context or use `useEffect` + state to detect dark mode client-side only.
