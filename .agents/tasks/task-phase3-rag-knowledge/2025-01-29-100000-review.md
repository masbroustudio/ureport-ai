# RAG pipeline and Knowledge Base for document-grounded chat

Phase 3 adds a complete retrieval-augmented generation pipeline: document upload (PDF/DOCX/TXT), token-based chunking, embedding via fastembed, Qdrant vector storage, retrieval at chat time, and citation SSE events back to the frontend. The frontend gains a Knowledge Base management page and a document selector in the chat composer that pipes `kb_document_ids` through to the backend. The approach is synchronous ingestion within the request lifecycle, per-user Qdrant collections for isolation, and a single system-prompt injection for RAG context.

**Watch for:** Synchronous ingestion blocks the HTTP request for the entire load-chunk-embed-upsert cycle, which will timeout on large documents (confirmed). Qdrant vector upsert succeeds before the DB commit, creating an inconsistency window if the commit fails (confirmed). The upload endpoint doesn't link the saved file to `source_file_id`, orphaning the storage record (confirmed). The `knowledge.py` delete endpoint silently swallows Qdrant failures, leaving stale vectors with no recovery path (confirmed).

## High-level view

The ingestion pipeline runs inside the upload request handler: file lands on disk, the loader extracts text, the chunker splits by paragraph/sentence boundaries at 512 tokens with 15% overlap, fastembed produces 384-dim vectors, and the Qdrant client upserts them into a per-user collection. Because this is synchronous, response latency equals document-processing time. A 100-page PDF will block for tens of seconds.

Retrieval embeds the user's query, queries Qdrant with an optional document-ID filter, formats the top-K results as numbered citation blocks, and injects them as a system message at position 0 in the LLM context. Citation metadata is streamed as SSE events after the text response completes.

The data model has a gap: `KnowledgeDocument.source_file_id` is never populated during upload, so there's no FK relationship between the uploaded file on disk and its knowledge document record. The file is saved via `save_upload_file` but only the path is used for ingestion; no `File` record is created.

Vector and relational storage are not transactionally coupled. The ingestion function upserts to Qdrant before committing to Postgres. If the DB commit fails, vectors exist in Qdrant with no corresponding `kb_chunks` rows. The delete path has the inverse problem: it deletes from Qdrant first (swallowing errors) then deletes DB records.

When both `file_ids` and `kb_document_ids` are provided in a single message, the data-analysis system prompt is inserted first, then the RAG context is inserted at position 0, pushing the data-analysis prompt to position 1. The LLM sees the RAG instruction as highest priority — determined by insertion order rather than explicit precedence logic.

<summary>Issues (9)</summary>

1. **Synchronous ingestion blocks request** (confirmed) — Large documents will timeout the HTTP request. Move ingestion to a background task or at minimum return 202 with a polling status endpoint.
2. **Qdrant-before-commit inconsistency** (confirmed) — `ingest_document` upserts vectors to Qdrant then commits to Postgres. If the commit fails after rollback, vectors are orphaned in Qdrant with no cleanup. Reverse the order or add a compensating delete on commit failure.
3. **`source_file_id` never populated** (confirmed) — The upload endpoint saves the file and creates a `KnowledgeDocument` but never sets `source_file_id`, making the FK column dead weight and preventing file-lifecycle cleanup.
4. **Silent Qdrant failure on delete** (confirmed) — `delete_document` catches all Qdrant exceptions with `pass`. If Qdrant is unreachable, the DB records are deleted but vectors remain searchable indefinitely. Log the error and consider failing the request or queuing a retry.
5. **No file-size guard on embedding batch** (confirmed) — `embed_texts` sends the entire chunk list to fastembed in one call. A document producing thousands of chunks could spike memory. Batch the embedding calls (e.g., 256 chunks at a time).
6. **Uploaded file not cleaned up on ingestion failure** (confirmed) — When ingestion fails and status is set to `"failed"`, the file remains on disk. No mechanism exists to retry or clean up the orphaned file.
7. **VectorStore instantiated per-call** (confirmed) — Every retrieval and ingestion creates a new `QdrantClient` TCP connection. Use a singleton or module-level instance to avoid connection churn.
8. **Embedder singleton race condition** (likely) — The lazy `_get_model()` has no lock. Concurrent requests can double-initialize the model, wasting memory during the race window. Add a `threading.Lock`.
9. **RAG + data-analysis prompt ordering is implicit** (confirmed) — When both features are active, RAG context lands at position 0 and data-analysis at position 1 purely due to code ordering. Make the precedence explicit or document the intended behavior.

## Ingestion lifecycle and the synchronous bottleneck

The upload endpoint in `knowledge.py` calls `ingest_document` directly inside the request handler. For a 200-page PDF with ~400 chunks, the embedding step alone (fastembed running on CPU) could take 10-30 seconds. The deployment notes acknowledge this limitation, but there's no timeout guard, progress reporting, or 202/polling mechanism.

The error path sets `status = "failed"` with a truncated error message on any exception. But the file on disk is never removed, and there's no retry affordance.

## Qdrant-Postgres consistency gap

In `ingest.py`, the sequence is:

```python
vector_store.upsert_chunks(user_id, qdrant_points)  # Qdrant write
db.add_all(chunk_records)                            # staged in session
doc_record.status = "ready"
await db.commit()                                    # Postgres write
```

If `db.commit()` raises, the except block calls `db.rollback()` and sets status to `"failed"`. But the vectors already exist in Qdrant — searchable, with no corresponding `kb_chunks` rows. The retriever queries Qdrant directly and returns results based on payload metadata, so these orphaned vectors will appear in search results pointing to a document marked as "failed".

The delete path in `knowledge.py` has the inverse coupling:

```python
try:
    vector_store.delete_document(...)
except Exception:
    pass  # Qdrant may not be available
```

DB records get deleted even if Qdrant deletion fails, leaving stale vectors that will match future queries and return payloads referencing a now-nonexistent document.

## Embedder singleton and concurrency

```python
def _get_model() -> TextEmbedding:
    global _model
    if _model is None:
        from fastembed import TextEmbedding
        _model = TextEmbedding(model_name=MODEL_NAME)
    return _model
```

Under concurrent requests, two threads could race past the `if _model is None` check and initialize the model twice. The double model load wastes memory and CPU during the race window. A `threading.Lock` around initialization is the standard fix.

## Chunker page-metadata tracking

The chunker assigns `current_page` from the first segment in the current chunk buffer and only updates it when a new chunk starts. A chunk spanning pages 1-2 is tagged only with page 1. This means citations may reference the wrong page for content near page boundaries — worth noting in documentation as a known limitation.

## RAG context injection positioning

When both `file_ids` and `kb_document_ids` are provided:

1. Data-analysis system prompt is inserted at position 0
2. RAG context is inserted at position 0, pushing data-analysis to position 1

The LLM sees RAG instructions first. This ordering is accidental — driven by code execution order in the handler rather than deliberate precedence design. If both features are commonly used together, the interaction should be explicitly designed (e.g., a combined system prompt template).
