# LLM-powered report generation pipeline (v2)

Phase 4 adds a multi-step report generation system: Gemini plans an outline, Cerebras/Llama 70B writes each section, and Jinja2+WeasyPrint renders PDF (with HTML fallback). The frontend provides outline editing, SSE-streamed progress, and PDF download. This is a second review pass; all six v1 issues (path traversal, concurrency guard, dead fields, error leaks, zombie reports, unsanitized download path) have been addressed.

**Watch for:** the `regenerate_section` endpoint and SSE error handler still expose raw exception strings to clients (confirmed); the PDF download link in the frontend uses a plain `<a href>` that cannot attach an auth header, so the request will always 401 (confirmed); Jinja2 renders LLM-generated HTML without autoescaping, creating a stored-XSS vector in the HTML output (confirmed).

## High-level view

The v1 error-message fix was applied to `create_report` (which now stores a generic message), but two other code paths — `regenerate_section` and the SSE render-failure handler — still interpolate `str(e)` directly into the HTTP response or SSE event. LLM client exceptions can contain API keys or internal URLs, so these are the same class of information disclosure that v1 issue #4 identified.

The frontend's PDF download is an `<a>` tag pointing at the API URL. Browsers do not attach `Authorization` headers on navigation requests. Since the download endpoint requires `get_current_user` (Bearer token), this link will always fail with 401 unless the user manually copies the token. The SSE `/start` endpoint works because the frontend uses `fetch` with explicit headers, but download uses a different mechanism.

The renderer calls `Template(f.read())` (Jinja2) without autoescaping, then injects `section.content_html` — which is LLM-generated markdown converted to HTML — via `{{ section.content_html }}`. Since the template has no autoescaping and the content is inserted raw, any HTML/JS the LLM produces (or is prompted to produce via crafted section instructions) ends up in the rendered output. For the PDF path this is largely contained by WeasyPrint (no JS execution), but the HTML fallback path serves this file directly to the browser with `text/html` content type.

Test coverage for the report pipeline remains incomplete. The SSE `/start` endpoint, `regenerate_section`, `download_pdf`, and `write_full_report` are still not tested.

<summary>Issues (4)</summary>

1. **Error message leak in regenerate_section and SSE error handler** — `regenerate_section` returns `f"Failed to regenerate section: {e}"` and the SSE render-failure path yields `json.dumps({"error": str(e)})`. Replace with generic messages; log the full exception server-side.
2. **PDF download link always 401** — The frontend uses `<a href=...>` for the download link, which can't attach Bearer tokens. Switch to a `fetch`-based download that sets the auth header, then creates a blob URL, or implement a short-lived signed URL / cookie-based auth for the download endpoint.
3. **Stored XSS via HTML fallback** — The Jinja2 template uses `{{ section.content_html }}` without autoescaping. When WeasyPrint is unavailable and the file is served as `text/html`, any script tags in LLM output execute in the user's browser. Either enable Jinja2 autoescaping and use `|safe` only after sanitization, or sanitize the markdown-to-HTML output (e.g., with `bleach` or an allowlist).
4. **No test coverage for critical paths** — The SSE generation endpoint, section regeneration, PDF download, and `write_full_report` remain untested. These are the most complex code paths in the system.

## Error message disclosure in remaining endpoints

The `create_report` endpoint now correctly stores `"Report planning failed. Please try again."` and logs the full exception with `exc_info=True`. Two other paths did not receive the same treatment:

```python
# regenerate_section (reports.py ~line 379)
raise HTTPException(
    status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
    detail=f"Failed to regenerate section: {e}",
)
```

```python
# SSE render failure (reports.py ~line 262)
error_data = json.dumps({"error": str(e)})
yield f"event: error\ndata: {error_data}\n\n"
```

Both pass the raw exception to the client. The fix is the same pattern already applied to `create_report`: generic detail for the client, `logger.error(..., exc_info=True)` for operators.

## PDF download auth mismatch

The frontend detail page renders:

```tsx
<a
  href={`${API_BASE}/api/v1/reports/${reportId}/pdf`}
  className="..."
>
  Download PDF
</a>
```

Browser navigation to this URL does not include the `Authorization: Bearer ...` header stored in localStorage. The backend's `download_pdf` depends on `get_current_user` which reads the Bearer token from the `Authorization` header. The result is an unconditional 401.

The SSE generation endpoint works because the frontend uses `fetch` with explicit headers. The download link needs the same treatment: either fetch the file as a blob and trigger a download via `URL.createObjectURL`, or the backend can issue a short-lived signed URL or accept a query-string token for this single endpoint.

## XSS surface in HTML fallback rendering

The renderer converts LLM-written markdown to HTML using `md.markdown(...)` with no sanitization, then inserts it into a Jinja2 template loaded with `Template(f.read())`. `jinja2.Template` defaults to `autoescape=False`, so `{{ section.content_html }}` is rendered as raw HTML.

Under the primary path (WeasyPrint generates PDF), this is low-risk because WeasyPrint does not execute JavaScript. Under the fallback path, the file is served as `text/html` via `FileResponse`:

```python
media_type = "text/html"
```

If an attacker can influence section instructions to make the LLM produce `<script>` tags, or if the LLM hallucinates a script block, the HTML file served to the user becomes an XSS payload. The mitigation is straightforward: either use `jinja2.Environment(autoescape=True)` and mark content_html with `Markup()` after sanitizing with an HTML allowlist, or strip `<script>`, `<iframe>`, `on*` attributes from the converted HTML before template insertion.

## Test coverage gaps

The test suite covers CRUD endpoints, the planner, the writer, and the renderer individually. Not tested:

- `POST /{report_id}/start` — the SSE endpoint that orchestrates writing + rendering with progress streaming and the new `finally`-block cleanup
- `POST /{report_id}/sections/{section_id}/regenerate` — includes the unfixed error leak
- `GET /{report_id}/pdf` — includes the path validation logic that was added as a v1 fix
- `write_full_report` in `writer.py` — the function that coordinates multi-section writing with DB updates
- Adversarial `template_id` values hitting `validate_template_id` — the fix was added but no test exercises it

The most important gap is the SSE endpoint: it contains the concurrency guard, the zombie-report cleanup, and the render step, all of which were v1 fixes that should be verified by tests.
