# LLM-powered report generation pipeline with SSE streaming

Phase 4 adds a multi-step report generation system: a Gemini-powered planner produces an outline, Cerebras/Llama 70B writes each section, and a Jinja2+WeasyPrint renderer produces PDF (with HTML fallback). The frontend provides outline editing, SSE-streamed progress, and PDF download.

**Watch for:** path traversal via user-controlled `template_id` reaching the filesystem (confirmed); the download endpoint serves files from an unsanitized DB-stored path (confirmed); the SSE generation endpoint has no guard against concurrent starts for the same report (likely); `custom_instructions` and `file_ids`/`kb_document_ids` from `ReportCreate` are accepted but silently ignored (confirmed).

## High-level view

The `template_id` is a user-supplied string that gets interpolated directly into a filesystem path (`Path(__file__).parent / "templates" / template_id`) with no validation beyond checking that `meta.yaml` exists. A value like `../../alembic/versions` would traverse outside the templates directory. The same unsanitized `template_id` flows to the renderer when it loads `layout.html.j2` and `styles.css`.

The SSE-based `/start` endpoint performs the entire write+render pipeline within a single streaming response. There is no mechanism preventing two concurrent POST requests from writing the same report's sections simultaneously, which would produce interleaved DB writes and a corrupted output file. If the client disconnects mid-stream, the report is left stuck in "writing" status with no recovery path.

Several fields accepted by `ReportCreate` (`file_ids`, `kb_document_ids`, `custom_instructions`) are never forwarded to the planner — it receives only `body.title` as the `user_request`. The `custom_instructions` field is presumably the most important user input for directing the outline, making this a significant functional gap.

The download endpoint (`GET /{report_id}/pdf`) serves whatever file path is stored in `report.pdf_path` via `FileResponse`. Under normal operation the renderer writes to a controlled `STORAGE_DIR`, but the path stored in the DB is never validated at serve time.

<details>
<summary>Issues (6)</summary>

1. **Path traversal in template_id** — `_load_template_meta` and `render_pdf` interpolate the user-supplied `template_id` directly into a filesystem path. Validate that it contains only alphanumeric characters, underscores, and hyphens, or resolve the path and confirm it stays within the templates directory.
2. **No concurrency guard on report generation** — Two simultaneous POSTs to `/{report_id}/start` will interleave section writes and DB commits. Add a status check-and-set (e.g., reject if status is not `created`) atomically at the start of generation, or use a DB advisory lock.
3. **Dead schema fields** — `file_ids`, `kb_document_ids`, and `custom_instructions` in `ReportCreate` are accepted but never used. Either wire them through to `plan_report_outline` or remove them to avoid confusing API consumers.
4. **Error message leaks internal state** — The `create_report` endpoint stores `str(e)` in `error_message` and returns it to the client. LLM client exceptions can contain API keys or internal URLs. Sanitize or generalize the stored message.
5. **SSE endpoint leaves zombie reports on disconnect** — If the client disconnects mid-stream, the async generator stops but no `finally` block resets the report status. The report stays stuck at "writing" permanently with no retry mechanism.
6. **Download endpoint serves unsanitized path** — `FileResponse(path=report.pdf_path)` trusts the DB value. Add a check that the resolved path is within `STORAGE_DIR`.

## Path traversal in template loading

The `_load_template_meta` function in `planner.py` constructs a filesystem path directly from user input:

```python
template_dir = Path(__file__).parent / "templates" / template_id
meta_path = template_dir / "meta.yaml"
```

The `template_id` field in `ReportCreate` defaults to `"business_report_v1"` but accepts any string. A request with `template_id = "../../"` or `template_id = "../../../etc"` would traverse outside the templates directory. In the planner this would likely fail (no `meta.yaml` at the target), but the renderer uses the same pattern to load `layout.html.j2` — if an attacker can place or find a file named `layout.html.j2` elsewhere in the tree, it would be rendered as a Jinja2 template with full access to the Jinja2 sandbox (or lack thereof, since `Template()` is used without sandboxing). The fix is a simple allowlist or regex validation (`^[a-zA-Z0-9_-]+$`) on `template_id` before it reaches the filesystem.

## Concurrent generation and stale status

The SSE endpoint reads the report, checks for an outline, then starts writing. There is no atomicity between checking the status and setting it to `"writing"`. Two requests arriving simultaneously will both pass the `if not report.outline_json` check, both set status to "writing", and both iterate through the sections concurrently against the same DB rows. Since the endpoint calls `db.commit()` after each section, the interleaving would produce unpredictable `content_markdown` values.

A minimal fix: check `report.status == "created"` and reject with 409 if already in-progress. A stronger approach would use `SELECT ... FOR UPDATE` to make the transition atomic.

## Unused schema fields and prompt construction gap

`ReportCreate` accepts `file_ids`, `kb_document_ids`, and `custom_instructions`, but the router passes only `body.title` to the planner:

```python
outline = await plan_report_outline(
    user_request=body.title,
    file_profiles=None,        # always None
    kb_doc_summaries=None,     # always None
    template_id=body.template_id,
)
```

The planner is guided solely by the report title. Custom instructions, file context, and KB document context are all discarded despite being accepted by the API.

## Error message information disclosure

When the planner fails, the full exception string is stored and returned:

```python
except Exception as e:
    report.error_message = str(e)
```

Exceptions from `litellm.acompletion` can include request URLs, partial API keys, or internal stack context. Store a generic user-facing message and log the full exception server-side only.

## Report lifecycle and SSE cleanup

The `event_stream()` async generator has no `finally` block. If the client disconnects mid-stream, the report remains at `status="writing"` with partial progress indefinitely. There's no API endpoint to reset or retry a stuck report. A `try/finally` that sets `status="failed"` on incomplete state, plus a mechanism to re-trigger from "failed", would close this gap.

## Test coverage gaps

28 tests cover the planner, writer, renderer, and CRUD endpoints. Not tested:

- The SSE `/start` endpoint — the most complex code path with async generator, multiple commits, LLM calls, and rendering.
- The `regenerate_section` endpoint.
- The `download_pdf` endpoint.
- The `write_full_report` function in `writer.py`.
- Adversarial `template_id` values.
